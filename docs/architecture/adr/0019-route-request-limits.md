# ADR-0019: Route request limits. Per-costing distance and location limits in Valhalla's own `service_limits`, applied at serve time; an 8 s Valhalla processing timeout inside the 10 s gateway timeout; a gateway concurrency cap on `/v1/route` answered with 503 `RoutingBusy`

- **Status:** accepted (architect, 2026-10-11; implementation record filled in the Verify stage the same day). The values and behaviour visible to users are PO decisions: D213, then D216–D225 ("All as recommended", 2026-10-11). This ADR records the technical design that implements them.
- **Date:** 2026-10-11
- **Stories:** SEC-2 (audit finding BE-1 medium "Route request cost is unbounded: Valhalla DoS"; threat model rows 1.5 and 2.6; release checklist B10). There is no SEC-2 story (D224). The work is recorded as change logs on NAV-001 AC 44–49 (main), NAV-004 AC 35/36, NAV-005 AC 7/49, NAV-011 AC 24, NAV-018 AC 17, NAV-021 AC 6/7 and NAV-008 AC 13. Task breakdown: [`tasks/SEC-2-route-request-limits.md`](../tasks/SEC-2-route-request-limits.md).
- **Contract:** `openapi.yaml` **0.6.1 → 0.7.0**. It is additive (new 503 `RoutingBusy`, `GatewayError` code, examples, texts), with one documented narrowing: `locations` `maxItems` drops from 20 to 10. No contracted client sends more than 2 locations.
- **Touches:** ADR-0002 §3 (gateway responsibilities: a new error mapping on `/v1/route`), ADR-0014 (every slot gets the limits), ADR-0017 (Amendment A6: device limits stay unchanged), `deployment-staging.md` §7.

## Context
`/v1/route` forwards any Valhalla `/route` body unchanged (ADR-0002 pass-through). Today nothing bounds what one request may cost, or how many requests may run at once. One client can tie up every Valhalla worker with a few far or many-stop requests. The tester-only staging host (NAV-008) and any later public host have no authentication (D8), so the gateway and Valhalla must bound the cost themselves. D213 asked for: car at most 10 stops and 3,000 km; walk and bike limits, a Valhalla timeout and a concurrency cap set by the architect; a defined error; a Mongolian message.

Facts (read 2026-10-11 from the repository and the generated config; nothing new was measured in this design run):

- **F1. Current Valhalla limits.** These are Valhalla 3.9.0 defaults, generated by `valhalla_build_config` in `backend/scripts/valhalla-build.sh` `make_config`. The only override is `--service-limits-max-alternates 2`. From `data/valhalla/valhalla.json`:

  | `service_limits` section | `max_distance` | `max_locations` |
  |---|---|---|
  | `auto`, `taxi`, `truck` | 5,000 km | 20 |
  | `bus` | 5,000 km | 50 |
  | `auto_pedestrian` | 5,000 km | (none) |
  | `bicycle`, `motorcycle`, `motor_scooter`, `bikeshare`, `multimodal`, `transit` | 500 km | 50 |
  | `pedestrian` | 250 km | 50 |
  | `isochrone`, `centroid`, `trace` | 25 / 200 / 200 km | 1 / 5 / – |

  `httpd.service.timeout_seconds` is `-1` (never). `httpd.service.interrupt` is `ipc:///tmp/interrupt`.
- **F2. Upstream semantics, documented in upstream help text.** The backend measured them in the Verify stage; the implementation record at the end wins where it differs.
  - (a) `max_distance` is documented as the "maximum b-line distance between all locations in meters" (help text in `valhalla_build_config`). That is the summed straight line, checked in loki before snapping, with error 154 → OSRM `DistanceExceeded`. For 2 locations, summed and per-pair give the same result.
  - (b) More than `max_locations` gives error 150 "Exceeded max locations". The expected OSRM code was `TooBig`; the measured code is `InvalidValue` (implementation record).
  - (c) `timeout_seconds` is documented as "how long to wait for a single request to finish before timing it out". The `interrupt` socket is documented as "used to cancel work in progress". Measured: a plain-text 504 about 1 s after the configured value. Whether the route computation actually stops at that point could not be measured.

  The contract follows the measurement (`openapi.yaml` 0.7.0, Verify stage).
- **F3. Gateway.**
  - The `/v1/route` location has `error_page 502 503 = @route_unavailable`, which always answers **502** `UpstreamUnavailable`, and `proxy_intercept_errors off` (`snippets/proxy-common.conf`). An nginx-generated 503, which is the default `limit_conn_status`, would therefore surface as a mislabelled 502.
  - A Valhalla 5xx response passes through raw. Valhalla's own CORS header is hidden, but its body is not JSON `GatewayError`.
  - Rate limits (`limit_req`, NAV-008) are generated by `entrypoint/16-rate-limits.sh` and are off in dev.
- **F4. Config drift.** `valhalla.json` is written only when the graph is built. The build marker fingerprint is `osm=<sha> valhalla=<version>`, so a config-only change never reaches an existing `data/` build or an existing NAV-006 slot. Both Valhalla services mount the data **read-only**.
- **F5. Device.** The Android on-device engine (`valhalla-mobile` 0.6.3, ADR-0017) uses the AAR's own `default.json` `service_limits`: `auto` 5,000 km / 20, `bicycle` 500 km / 50, `pedestrian` 250 km / 50. ADR-0017 A1 F1 says these equal the server's values, and both sides assert that the device config does not override them.
- **F6. Clients.**
  - The web `routeClient.ts` and Android `RouteOutcome.kt` already classify 502, 503 and 504 as "unavailable" by status.
  - Both parse `DistanceExceeded`, and map it to "no route" on car.
  - Android reroute already treats `TooFar` like `NoRoute` (`ReroutePolicy`).
  - Clients always send exactly 2 locations.

## Decision

### 1. Distance and location limits live in Valhalla's `service_limits`, for every costing
Valhalla checks them in loki before any graph search, so an over-limit request costs microseconds and returns 400 within 1 s. The pass-through stays intact: the gateway does not parse bodies.

**Values (D216, D217, D222).** Rule: every `service_limits` section that has a `max_locations` above 10 gets **10**, and every section that has a `max_distance` above 3,000 km gets **3,000 km**. Sections that are already lower keep their values. The result:

| Section | `max_distance` | `max_locations` | Why |
|---|---|---|---|
| `auto` | **3,000,000 m** | **10** | D213 / D216 / D222 |
| `bus`, `taxi`, `truck` | **3,000,000 m** | **10** | No costing bypass: the pass-through forwards them although clients never send them |
| `auto_pedestrian` | **3,000,000 m** | (none) | Same rule. It is not reachable as a `/route` costing, but it is capped anyway so the rule has no exceptions |
| `bicycle` | 500,000 m (unchanged) | **10** | D217; equals the device and the Valhalla default |
| `motorcycle`, `motor_scooter`, `bikeshare`, `multimodal`, `transit` | 500,000 m (unchanged) | **10** | Same rule |
| `pedestrian` | 250,000 m (unchanged) | **10** | D217; NAV-004 RS8 (P1→X1 on foot, about 245 km) stays 200 |
| `isochrone`, `centroid`, `trace`, `max_alternates` (2) | unchanged | unchanged | Already lower. Their actions are not proxied: the gateway exposes only `/route` |

**One source, applied at serve time (the answer to F4).**
- **One source for the values.** One shell function in `backend/scripts/lib.sh` (proposed name `valhalla_limit_args`) emits the `valhalla_build_config` flags for the table above and the timeout from §2. Both scripts below use it.
- **Serve time is authoritative.** `valhalla-serve.sh` starts `valhalla_service` with a **container-local runtime config**, for example `/tmp/valhalla.json`. This file is the slot's or `data/`'s `valhalla.json` with `service_limits` and `httpd.service.timeout_seconds` overlaid. A small `python3` step is enough; it is already in the Valhalla image for `valhalla_build_config`. The data mount stays read-only. As a result, a `data/` build made before SEC-2 (NAV-001 AC 2 path, no rebuild), every existing NAV-006 slot, both blue and green lanes, and the slot verification stack all serve the limits. None of them needs new OSM data.
- **The build also writes the limits.** `valhalla-build.sh` `make_config` adds the same flags, so a freshly built `valhalla.json` describes what is served.
- **The limit values are not part of the build fingerprint.** Changing a limit must never trigger a graph rebuild.
- **Startup log line.** `valhalla-serve.sh` logs the effective values once, for example `auto=3000km/10 pedestrian=250km/10 bicycle=500km/10 timeout=8s`. This line contains no personal data and lets QA and slot verification read what is enforced.

**Not changed.** Gate 2 (`backend/gate2/default.json`, `nav_pack.py`) and the device config. See §5.

### 2. Timeout chain: Valhalla 8 s < gateway 10 s < client 12 s (D218)
- **Valhalla.** `httpd.service.timeout_seconds` = `VALHALLA_TIMEOUT_SECONDS`, default **8**, an integer from 1 to 9. Measured granularity is about 1 s (implementation record), so the default answers after about 8–9 s. A value of 9 can race the 10 s gateway read timeout; either way the client gets the same 504 `UpstreamTimeout` JSON, so 9 stays allowed, but 8 is the recommended maximum. A value of 10 or more would never fire before the gateway timeout, so an invalid value makes `valhalla-serve.sh` refuse to start, with a log line. This matches the rule in `16-rate-limits.sh` that invalid values stop the service. The key is passed to the `valhalla` service in `compose.yaml` and to both lanes in `compose.slots.yaml`. It also goes to `valhalla-build` if `make_config` reads it.
- **Gateway.** `proxy_read_timeout 10s` on `/v1/route` stays, as do the client timeouts (web and Android 12 s). NAV-004 AC 36, NAV-005 AC 7/48 and NAV-021 AC 10 do not change.
- **Shaping.** In the `/v1/route` location only:
  - turn on `proxy_intercept_errors on`;
  - map upstream 500, 502 and 503 to `@route_unavailable` (status 502) and upstream 504 to `@route_timeout` (status 504 `UpstreamTimeout`, or 502 when the connect never completed, as today). Upstream 500 was added in implementation and is confirmed in the Verify stage: the contract says every 5xx on `/v1/route` is a gateway `GatewayError`, so no raw Valhalla 5xx body may reach a client.

  The location has no `error_page 400`, so Valhalla's 400 bodies still pass through unchanged. **`error_page 400` must never be added there.** The location's existing `error_page 404/405/413/429` would now also catch the same codes from Valhalla. Valhalla does not send these for `/route`, and if it ever did, the client would get the gateway's documented JSON for that status, which the contract already lists for this path.
- **What the Valhalla timeout buys (F2c).** At minimum, the client gets a defined 504 at 8 s instead of a hanging request. That is the contract guarantee. Whether the worker also stops computing depends on Valhalla's interrupt handling and is measured by the backend (NAV-001 AC 48, informational bullet). **The design does not depend on it.** Per-request cost is bounded by §1, and the work in flight is bounded by §3: at most the global cap of requests can be computing or queued inside Valhalla at once.

### 3. Concurrency cap at the gateway: nginx `limit_conn`, global + per IP, 503 `RoutingBusy`, no queue (D219)
- **Zones.** These are http-level, generated by a **new entrypoint `backend/gateway/entrypoint/17-route-limits.sh`** into `conf.d/02-route-limits.conf`. The script is separate from `16-rate-limits.sh` because the cap is always on and the rate limits are not. It follows the same pattern:
  - `map $request_method $nav_rc_client { OPTIONS ""; default $binary_remote_addr; }`
  - `map $uri $nav_rc_ip_key { /v1/route $nav_rc_client; default ""; }` and a constant global key `map $uri $nav_rc_global_key { /v1/route <constant, for example "route"> ; default ""; }`. OPTIONS gets the empty key too.
  - `limit_conn_zone $nav_rc_global_key zone=nav_route_global:1m;` and `limit_conn_zone $nav_rc_ip_key zone=nav_route_ip:10m;`
  - `limit_conn nav_route_global ${GATEWAY_ROUTE_MAX_INFLIGHT};` `limit_conn nav_route_ip ${GATEWAY_ROUTE_MAX_INFLIGHT_PER_IP};` at http level. They are inherited everywhere but count only `/v1/route` GET and POST, because nginx does not account requests with an empty key. Health, tiles, search, reverse, packs and preflights are never counted.
  - `limit_conn_log_level info;`, below the gateway's `crit` error log, so client IPs never reach the logs (NFR-P1), as for `limit_req`.
  - `limit_conn_status 529;` is a **private status** that is never sent to clients (see the next bullet).
  - Validation: both values must be integers ≥ 1, otherwise the gateway refuses to start. There is no "off" value: the cap is always on (NAV-001 AC 49). To effectively disable it for a load test, set a high value.
- **The cap cannot be silently off.** The `/v1/route` location reads `$nav_rc_ip_key` (`set $nav_rc_guard $nav_rc_ip_key;`). That variable exists only in `conf.d/02-route-limits.conf`, so `nginx -t` fails and the gateway does not start when `17-route-limits.sh` is not mounted or did not run. Every gateway definition (dev `compose.yaml`, both `compose.slots.yaml` gateways, the QA isolated gateway, CI) must mount `entrypoint/17-route-limits.sh`. This is intended: a missing script is a deployment error, not a reason to serve without the cap.
- **Status split (F3).** In the `/v1/route` location, `error_page 529 = @route_busy`. The new named location answers **503**:
  - body `{"code":"RoutingBusy","message":"routing service busy"}`;
  - `add_header Retry-After 1 always`;
  - `add_header Cache-Control no-store always`;
  - the CORS snippet included **once**.

  `limit_conn` rejects in the preaccess phase, before any header filter has added CORS headers, exactly like `limit_req` and `@rate_limited`, so the snippet does not duplicate them. A private code keeps the cap separate from any upstream 503, which §2 maps to 502. Without the split, the cap would either be relabelled 502 or an upstream 503 would be relabelled `RoutingBusy`. The backend may choose a different private code in 400–599 that no upstream or nginx path produces, as long as the observable contract holds.
- **What is counted.** nginx counts a connection only while it has a request in progress, so idle keep-alive connections do not count. On staging, Caddy proxies with HTTP/1.1 and opens one upstream connection per concurrent request, so the count equals the number of route requests in flight. The per-IP key is the real client IP after `real_ip`, which the staging overlay always sets (`GATEWAY_REAL_IP_FROM`). Without it, every staging request would share Caddy's address and the per-IP cap would act as a global cap of 4. IPv6 is keyed per /128 until SEC-4A BE-2 re-keys the rate limits and this cap together, per /64.
- **Defaults: `GATEWAY_ROUTE_MAX_INFLIGHT=8`, `GATEWAY_ROUTE_MAX_INFLIGHT_PER_IP=4`.**
  - Global 8 = 2 × `VALHALLA_THREADS` on the 4-vCPU staging host: 4 computing plus at most 4 waiting inside Valhalla. With the 8 s timeout, the longest wait stays bounded.
  - Per IP 4 lets one CGNAT address hold half the capacity, not all of it.
  - These are **dev defaults** until the NAV-008 staging measurement (`deployment-staging.md` §7.2).
  - A normal client sends at most 1 route request in flight (web and Android preview; Android guidance: 1 in flight, ≥ 5 s apart), so a single user never meets the cap.
- **Interaction with the rate limits.** `limit_req` (429) and `limit_conn` (503) both run in preaccess. When both would reject, the client gets one of them. The contract allows either (openapi "Route concurrency cap").

### 4. No gateway route-length check, no body parsing
The 3,000 km is enforced as a straight-line sum (D216). The gateway never reads request or response bodies on `/v1/route`. ADR-0002's pass-through and the "no route bodies in logs" rule (NFR-P1) stay as they are.

### 5. Devices keep their limits (D221)
The on-device engine is not changed (ADR-0017 Amendment A6). The pack covers Mongolia only, and the longest straight line inside Mongolia is about 2,400 km. Clients send 2 locations. The only visible difference: a car point 3,000–5,000 km away shows N24 online and N9 offline. One endpoint of such a request is always outside the pack. The Gate 1 and Gate 2 golden sets must not contain such a pair, and must not contain requests with more than 10 locations.

### 6. Configuration keys (confirmed names)
| Key | Where | Default | Comment for `.env.example` |
|---|---|---|---|
| `VALHALLA_TIMEOUT_SECONDS` | `valhalla` (dev), both slot lanes; `valhalla-build` if `make_config` reads it | `8` | Valhalla per-request processing timeout in seconds (1–9, below the 10 s gateway timeout) → 504 UpstreamTimeout |
| `GATEWAY_ROUTE_MAX_INFLIGHT` | gateway (dev and slots) | `8` | Max /v1/route requests in flight in total; over it → 503 RoutingBusy (2 × VALHALLA_THREADS; tune on staging) |
| `GATEWAY_ROUTE_MAX_INFLIGHT_PER_IP` | gateway (dev and slots) | `4` | Max /v1/route requests in flight per client IP; over it → 503 RoutingBusy |

All three go into `backend/.env.example` and `infra/staging/.env.example` with these one-line comments (NAV-001 AC 3). The distance and location values are **not** keys. They are the contract (D216, D217, D222) and live in the `lib.sh` function. Changing them is an ADR note plus a contract change.

## Alternatives considered
| Option | Pros | Cons |
|---|---|---|
| **Chosen:** limits in Valhalla `service_limits` for every costing, applied at serve time; Valhalla timeout; nginx `limit_conn` cap with 503 | Rejects before any cost; no body parsing; works on old builds and every slot; config only, no fork | The private status trick and `proxy_intercept_errors` need care; worker release on timeout is unmeasured |
| Route-length check in the gateway (njs reads the response) | Matches the literal "3,000 km route distance" | Valhalla has already spent the cost, so it is no DoS protection. It buffers bodies, breaks the pass-through, and could reject real west–east routes over about 2,700 km (rejected by D216) |
| Limits only for `auto`, `pedestrian`, `bicycle` | Smaller change | `truck`, `bus` and `taxi` (5,000 km / 20–50 locations) bypass them through the pass-through, so BE-1 stays open |
| Gateway costing allow-list (only `auto`, `pedestrian`, `bicycle`) | Smaller surface | Needs body parsing in nginx/njs. Belongs to BE-15 (low), not needed to close BE-1 |
| Limits only at build time (`make_config`) | One place | Existing `data/` builds and slots keep the old limits until the next OSM change (F4) |
| Cap with 429 `RateLimited` | Existing code and client path | It blames the client's IP for a full server, and many phones share CGNAT addresses. Clients retry once automatically after 429, which adds load during overload (rejected by D219) |
| A short gateway queue (`limit_req` with delay, or nginx upstream `queue`) | Smooths bursts | Holds connections and sockets during overload, so queued requests time out at 10 s anyway. `queue` is nginx Plus only |
| Only `VALHALLA_THREADS`, no cap | No gateway change | Valhalla queues internally without a bound. Under a burst every request waits, and all of them time out together |
| Raise the gateway and client timeouts | Fewer 504s near the limits | Holds workers longer. It changes NAV-004 AC 36 and NAV-021 AC 10 (rejected by D218) |

## Consequences
- **BE-1 can close** once NAV-001 AC 44–49 pass (security-engineer verifies; checklist B10). Threat-model rows 1.5 and 2.6 move to "mitigated".
- **Clients:** one change only. 400 `DistanceExceeded` on car shows N24 (web `routeController.ts` / `routePreview.ts`; Android `PreviewController.kt` for both server and on-device `TooFar`). No change for 503, timeouts or the request bodies.
- **Contract:** 0.7.0. A caller that sends 11–20 locations now gets 400. No contracted client does.
- **Operations:** three new keys. The cap values need the NAV-008 staging measurement before any public exposure. A full cap shows up as `RoutingBusy` in client error states, never in the logs, because client IPs stay below `crit`. Monitoring can count 503s by status from the access log, which has no IP and no query string.
- **SEC-4A** (BE-2, BE-3, BE-4) runs strictly after SEC-2 (D225). BE-2 re-keys `nav_rc_client` together with `nav_rl_client`. BE-4 compose resource limits should keep `VALHALLA_THREADS` × 2 ≥ `GATEWAY_ROUTE_MAX_INFLIGHT`, or lower the cap.
- **NAV-008 rate-limit probe:** `rate_limit_check.py` burst-route (64 workers) now meets the cap first. It must accept 503 `RoutingBusy` in the contract shape next to 429. The normal scenario must still produce 0 errors.
- **Follow-ups not in scope:**
  - `exclude_polygons` / `exclude_locations` limits stay at the Valhalla defaults (`max_exclude_polygons_length` 10 km, `max_exclude_locations` 50). The security-engineer may raise them under BE-15.
  - Walk and bike latency near the limit (NAV-001 AC 47, R15): if P1→X1 on foot exceeds 8 s, the architect lowers the pedestrian limit (D217 allows it, never below the UB floor) as a note here, and the BA updates AC 47.

Implementation notes confirmed in review:
- The `lib.sh` table also caps `bikeshare`, `multimodal` and `transit` (500 km / 10) and applies a backstop to any other `service_limits` section, so no section is more permissive than the rule in §1.
- HEAD and any method other than GET/POST/OPTIONS get 405 in the rewrite phase, before `limit_conn` runs (preaccess), so they are never counted, although the `17-route-limits.sh` key maps give them a non-empty key.
