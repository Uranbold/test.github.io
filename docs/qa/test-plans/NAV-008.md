## 1. Scope and rules

In scope: AC 6 to 24 as listed in `deployment-staging.md` §15, the story's edge cases, and the openapi 0.4.0 additions (contract cases `CT8-*`).
AC 1 to 5 are architect and PO deliverables (spike, ADR, decisions). QA only checks that AC 8 values and the AC 24 record reach them.

Rules for every run:

- **Host-agnostic.** No host name, IP address or credential is committed. Scripts read `STAGING_HOST`, `BASE_URL`, `ALLOWED_ORIGINS` and the optional `STAGING_IPV4`/`STAGING_IPV6` from the environment or from `tests/staging/nav008/staging.local.env`. That file is git-ignored, and `staging.env.example` is its template. Raw outputs that contain an address (nmap, testssl) go to `tests/staging/nav008/results/`, which is also git-ignored. Reports print `<ipv4>`/`<ipv6>`.
- **No credentials.** No script asks for or sends a password or private key. SSH probes use `BatchMode=yes` with public-key auth disabled, so the server can only list the methods it accepts.
- **Shared dev stack.** The NAV-003 workflow uses `http://localhost:8080` at the same time. No burst is ever sent there: `staging_checks.py --group ratelimit` and `contract_nav008.py` refuse (`SKIP RL00.guard` / `SKIP CT8-R.all`) unless `NAV008_ALLOW_BURST=1`. Rate-limit behaviour is verified against the mock or an isolated gateway on another port (section 6).
- **Staging timing results carry the host and the AC 8 values** (story edge case, D26). Every report that shows a latency or timing lists the operator medians next to it.

## 4. The D26 latency rule and the order of AC 8 and AC 9

```
AC 6 on the operator ──> AC 8 c1 (20 samples) ──> RESULT?
                                               ├─ REPEAT (> 2 timeouts): rerun, the run does not count
                                               ├─ RECORDED, median ≤ 100 ms ──────────────────────────> AC 9 allowed
                                               └─ RECORDED FLAG_D26 (median > 100 ms)
                                                     └─> QA → orchestrator → PO: accept the measured value as the
                                                         D26 value (new decisions.md row) or ask for action
                                                         └─> PO response recorded ──> AC 9 with D26_PO_RESPONSE=recorded
```

- `phone-kit.sh route-p95` refuses to run while any `c1-summary-*.txt` in its results folder has `FLAG_D26` and `D26_PO_RESPONSE` is not `recorded`. So AC 9 cannot run before the PO has answered.
- Record per operator (goes to ADR-0005 via the architect and is referenced from D26):

| Operator | Network | District | Date, time (UB) | Egress ASN (holder) | n | Median ms | p95 ms | Timeouts | Result | PO response (if flagged) |
|---|---|---|---|---|---|---|---|---|---|---|

- The median is the mean of the two middle values for an even n; p95 is nearest-rank (19th of 20), as in spike §5.5. The metric is `time_connect − time_namelookup` on a new TCP connection per sample, with no proxy or VPN.
- The < 50 ms target does **not** apply to staging (D26). There is no hard ceiling unless the PO sets one (story open question).

## 7. Interpretations used (confirm with BA)

1. **AC 13 "normal session (≤ 10 requests/s to the API paths)"**: tested at 10 r/s to **one** path group at a time (route, then search+reverse), which is stricter than 10 r/s spread over all paths.
2. **AC 13 "any rate of tile range requests"**: 1,500 range requests as fast as 64 parallel connections allow (about 1,300 r/s locally). The achieved rate is reported.
3. **AC 13 burst**: the 100 r/s × 10 s rate must actually be reached (`RL07/RL10.rate_achieved` ≥ 90 %). If the QA client cannot send that fast, the run is invalid, not a product failure.
4. **AC 9 warm-up**: a `GET /health` on the same connection opens it (TLS handshake), then the 20 `postRoute` requests are timed. The handshake is not part of the 20 samples. With a 100 ms RTT the handshake alone is about 200 to 300 ms.
5. **AC 7 redirect**: 301 passes the AC. The design expects Caddy's 308, so a 301 is reported to backend as INFO (a 301 turns a POST into a GET).
6. **AC 6 iPhone**: "if available". A missing iPhone is recorded, not failed.
7. **AC 12 "the SSH port"**: port 22 per design §4 (UFW `limit`). `SSH_PORT` changes it if the runbook uses another port.
8. **AC 14 sshd logs**: source IPs in the sshd journal are security logs outside the request path (design §8) and are reported as INFO for the counsel review, not as an AC 14 failure.
